# S, start to finish

Everything an S change needs, in one file: don't load `flow.md`, another reference or the templates. `$S` is `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/state.py"`, `$V` is `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/verify.py"`. The record is two files: `<change>` for people and the state file for the agent.

1. **Setup and paths:** name it `<yyyy-mm-dd>-s-<slug>` (the branch too). The `sdlc session status` line in your context gives setup, the paths (`<feature>` replaced by the name) and the remote; without it (another agent), run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/scaffold.py" status && python3 "${CLAUDE_PLUGIN_ROOT}/scripts/scaffold.py" paths <name>`. `setup none` → ask once whether to set it up (`/sdlc:setup`); no → go on and record it as a deviation.
2. **Understand it.** Read the code it touches, in one turn. Unclear what, why or how → ask, one question at a time. A bug: write the test that shows it, run only that test, and see it fail; find the root cause, not the symptom.
3. **Write the record and the tests in one turn**, as parallel writes with your file-writing tool, a few lines each:
   - `<state>` isn't written by hand: `$S new` in the call below writes it from its flags (`--task "<title> | <ACs> | <files>"` per task, each naming every file it changes; `--surface "<kind> <name> — <AC>"`, e.g. `--surface "export div — AC-001"` or `"dependency left-pad — AC-002"`, only for exports and dependencies the change adds or whose signature it changes, what `verify.py`'s drift check compares, none when there are none; new behaviour inside an existing one isn't surface).
   - `<change>`: `## Why` (what it's for, the request verbatim, and for a bug the proof and root cause), `## Decisions` (the decision and what was ruled out), `## Acceptance criteria` (`AC-001` …; a bug's AC-001 is the test that shows it), `## Acceptance tests`, `## Must never break`, `## Out of scope`. The table, exactly this shape (the Test cell is the file path, ` › `, the test name; `verify.py` parses it):
     ```
     | AC | Test | Run |
     |---|---|---|
     | AC-001 | tests/test_calc.py › test_add_positive | `python -m unittest tests.test_calc.T.test_add_positive` |
     ```
   - every AC's test (the bug's is already written).
   - Conventions on first touch: the change touches an area (layers, schema, contract, auth, data-access, ui) of its package's stack, named from the manifest as `flow.md`'s Define says, with no `.claude/rules/<stack>-<area>.md` yet (`python3 "${CLAUDE_PLUGIN_ROOT}/scripts/scaffold.py" conventions` lists the areas) → the task renders it first, `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/scaffold.py" conventions <stack> <area> [--package <name>]`, and names that file.
   - UI work (a changed path in `areas.ui`): read `ui-work.md` first; its `## UI mapping` goes into `<state>` after `$S new` writes it.
   Then one call: `$S new <name> --track S --risk low|high --footprint <n> --task "…" [--surface "…"] && $S advance <name> 2 --gate pass && $V red AC-001 AC-002 …` (no stop on S). If a test is refused, nothing is recorded: fix it and rerun the red step.
4. **Build.** Write the code, independent edits as parallel tool calls in one turn, running only the nearby tests. Most S changes get no review, so write against the recurring defects the brief printed: a failure reaches the user as a message, never a traceback, and data read back is checked like input. Then `$V` once: lint, typecheck, build, the full suite, each AC's test, drift. Fix until it passes. A change from the plan: `$S deviation <name> "<file or task> What: … Why: … Effect: …"`, one line.
5. **Review decision, by this list only.** Security when `Risk: high` or a changed path matches `areas.sensitive` or `areas.migrations` (the effective ones, plugin defaults included: `scaffold.py config`); UI when a changed path matches `areas.ui`; code when `## Public Surface` isn't `- none`. Nothing fires → none: the default for S, and no review this list doesn't name runs. Run each that fires once, fresh. Code, where this agent has the built-in `code-review` skill (Claude Code): that skill, `high --max-findings all`, the level always named, no `--fix`; rate its findings by `review-brief.md`'s Severity list and write them, each with your rating, as `{"findings": [{"id", "severity", "bug", "text"}]}` to a file with the Write tool, then run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/review_report.py" <name> --agent code-reviewer --round <N> --findings <file>` (`<N>` one more than the highest round already in `.sdlc/.work/findings/<name>/`, 1 when it is empty): it writes `code-reviewer-r<N>.md` and ends it with the verdict your ratings give (every high, and in round 1 every bug: FAIL). Otherwise, and for security and UI: on `opus` (its prompt: read `${CLAUDE_PLUGIN_ROOT}/skills/orchestrator/references/review-brief.md` `<change>`, the state file and `git diff <Base> -- . ':!.sdlc'`); highs, and any other finding that's a bug in code this change touched, go back to step 4 and are fixed test first without asking, fixing the class each finding names, not just the instance (`flow.md` Review step 3), then round 2 is the closing check (the failed review on the fixes and what calls them, told round 1's findings: each gone in every instance, no new bug; from round 2 only a high fails, and a medium or low bug it lists is fixed test first without another round); the rest (improvements, code it didn't touch) are tickets. When round 2 still fails, stop and ask the user (one more fix round, a waiver, or stop); a hook holds every edit and command until they reply. A review ran: append `## Review` to `<change>` with the Edit or Write tool (a shell heredoc is refused in Review) (what fired and so ran, verdicts, fixed, lessons filed, one line each).
6. **Ship.** S never enters Stage 3: go from 2 straight to 4. Learn: only a non-obvious lesson, via `sdlc:managing-knowledge`, linked in `## Review`; else nothing. One shell call: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ship.py" <name> --note "<review decision in a few words>" && git commit -F .sdlc/.work/commit-msg.txt && git push -u origin HEAD && gh pr create --fill`. When no review ran, add `--review "No review ran: no trigger fired."`. `ship.py` writes `## Review` from `--review` when none is there, reuses `$V`'s passing run (reruns it if code changed; with only baselined test failures, `--waive-baseline` lets it through and logs that), advances to Stage 4, sets `Status: done` (the commit carries the finished record), branches off the default branch, stages the change and writes a message from the change file's title naming `<change>` (`--message "<subject>"` overrides it; no backticks or `$`). No remote (`remote none`): stop after `git commit`. Then `gh pr checks --watch` (one CI fix, then ask; no remote or no checks: nothing to watch). End with a few lines: what changed, the test result, branch and commit (and the PR).

**A workbench** (`"workbench": true` and `workbench.json`, ADR 0025; the session starts there, the record lives there, the code in the app repos inside it): in step 3 the call starts with `git switch -c <name>` in the workbench, and `$S new` runs there, never in an app repo. In step 4, first `$S repo <name> <repo>` for each read-only repo the change reads, and before the first edit or command that changes an app repo, `$S repo <name> <repo>` for it (it branches the repo; a hook denies writes into one no feature has branched, and every write into a read-only repo); `$V` runs each branched repo's own commands. In step 6, `ship.py` also lists `repos` in merge order, each staged with its own message and PR body: for each, `git -C <path> commit -F <message> && git -C <path> push -u origin HEAD && gh pr create --body-file <pr_body>` from its folder, then `$S pr <name> <repo> <url>`; then commit and push the workbench's state file once more. `ship.py <name> --status` reports each PR and warns on an out-of-order merge.

**Always:** documents and the state file through your file-writing tool, never the shell. Before advancing, `Owner:` must be `git config user.email`; someone else's → say who and ask with the question tool. "Skip" / "just ship it": name the skipped steps, record a deviation, comply. Ask before merging, anything that adds scope, DB migrations or anything irreversible.

Stay inside the change: files the tests leave behind (`__pycache__`, caches) aren't drift and need no `.gitignore` edit; mention them in one line at most.

Anything that isn't S after all (a second area, an unclear cause, high risk that needs the user's call): stop, say so, and continue as M from `flow.md`.
