# S, start to finish

Everything an S change needs, in one file: don't load `flow.md`, another reference or the templates. `$S` is `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/state.py"`, `$V` is `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/verify.py"`. The record is two files: `<change>` for people and the state file for the agent.

1. **Setup and paths:** name it `<yyyy-mm-dd>-s-<slug>` (the branch too). The `sdlc session status` line in your context gives setup, the paths (`<feature>` replaced by the name) and the remote; without it (another agent), run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/scaffold.py" status && python3 "${CLAUDE_PLUGIN_ROOT}/scripts/scaffold.py" paths <name>`. `setup none` → ask once whether to set it up (`/sdlc:setup`); no → go on and record it as a deviation.
2. **Understand it.** Read the code it touches, in one turn. Unclear what, why or how → ask, one question at a time. A bug: write the test that shows it, run only that test, and see it fail; find the root cause, not the symptom.
3. **Write the record and the tests in one turn**, as parallel writes with your file-writing tool, a few lines each:
   - `<state>`: `# <name>`, `Status: active`, `Process: 2`, `Track: S   (footprint: <n> files)`, `Risk: low|high`, `Top model: opus`, `Base: <git rev-parse --short HEAD>`, `Owner: <git config user.email>`, `Tool: <agent>`, `Current: Stage 1 – Define`; then `## Tasks` (numbered, each naming its files in backticks), `## Public Surface` (only exports and dependencies the change adds or whose signature it changes, what `verify.py`'s drift check compares; new behaviour inside an existing one isn't surface; `- none` if none), and `## Gate log`, `## Deviations`, `## Open questions`, each with `-`.
   - `<change>`: `## Why` (what it's for, the request verbatim, and for a bug the proof and root cause), `## Decisions` (the decision and what was ruled out), `## Acceptance criteria` (`AC-001` …; a bug's AC-001 is the test that shows it), `## Acceptance tests`, `## Must never break`, `## Out of scope`. The table, exactly this shape (the Test cell is the file path, ` › `, the test name; `verify.py` parses it):
     ```
     | AC | Test | Run |
     |---|---|---|
     | AC-001 | tests/test_calc.py › test_add_positive | `python -m unittest tests.test_calc.T.test_add_positive` |
     ```
   - every AC's test (the bug's is already written).
   - UI work (a changed path in `areas.ui`): read `ui-work.md` first; it adds a `## UI mapping` to `<state>`.
   Then one call: `$S sync <name> && $S advance <name> 4 --gate pass && $V red AC-001 AC-002 …` (no stop on S). If a test is refused, nothing is recorded: fix it and rerun the red step.
4. **Build.** Write the code, independent edits as parallel tool calls in one turn, running only the nearby tests. Then `$V` once: lint, typecheck, build, the full suite, each AC's test, drift. Fix until it passes. A change from the plan: `$S deviation <name> "<file or task> What: … Why: … Effect: …"`, one line.
5. **Review decision, by this list only.** Security when `Risk: high` or a changed path matches `areas.sensitive` or `areas.migrations` (the effective ones, plugin defaults included: `scaffold.py config`); UI when a changed path matches `areas.ui`; code (default depth) when `## Public Surface` isn't `- none`. Nothing fires → none: the default for S, and no review this list doesn't name runs. Run each that fires once, fresh. Code, where this agent has the built-in `code-review` skill (Claude Code): that skill, `medium`, the level always named, no `--fix`; rate its findings by `review-brief.md`'s Severity list. Otherwise, and for security and UI: on `opus` (its prompt: read `${CLAUDE_PLUGIN_ROOT}/skills/orchestrator/references/review-brief.md` at default depth, `<change>`, the state file and `git diff <Base> -- . ':!.sdlc'`); highs go back to step 4. A review ran: append `## Review` to `<change>` (what fired and so ran, verdicts, fixed, lessons filed, one line each).
6. **Ship.** S never enters Stage 5: go from 4 straight to 8. Learn: only a non-obvious lesson, via `sdlc:managing-knowledge`, linked in `## Review`; else nothing. One shell call: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ship.py" <name> --note "<review decision in a few words>" && git commit -F .sdlc/.work/commit-msg.txt && git push -u origin HEAD && gh pr create --fill`. When no review ran, add `--review "No review ran: no trigger fired."`. `ship.py` writes `## Review` from `--review` when none is there, reuses `$V`'s passing run (reruns it if code changed), advances to Stage 8, sets `Status: done` (the commit carries the finished record), branches off the default branch, stages the change and writes a message from the change file's title naming `<change>` (`--message "<subject>"` overrides it; no backticks or `$`). No remote (`remote none`): stop after `git commit`. Then `gh pr checks --watch` (one CI fix, then ask; no remote or no checks: nothing to watch). End with a few lines: what changed, the test result, branch and commit (and the PR).

**Always:** documents and the state file through your file-writing tool, never the shell. Before advancing, `Owner:` must be `git config user.email`; someone else's → say who and ask. "Skip" / "just ship it": name the skipped steps, record a deviation, comply. Ask before merging, anything that adds scope, DB migrations or anything irreversible.

Stay inside the change: files the tests leave behind (`__pycache__`, caches) aren't drift and need no `.gitignore` edit; mention them in one line at most.

Anything that isn't S after all (a second area, an unclear cause, high risk that needs the user's call): stop, say so, and continue as M from `flow.md`.
