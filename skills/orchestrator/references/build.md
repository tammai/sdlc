# Build (Stage 4)

The builder works like plain Claude: it writes the code and its tests, with no review agents during the build. It works from `<change>` and the state file's plan sections (if they're already in this session's context, from that; after `/clear` or in a new session, from the files). `$V` below is `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/verify.py"`: type the full command each time, never a variable or alias, or the hooks won't recognise the run.

- **How it runs:** as `## How the build runs` says (Define's call): inline in this session; one part per fresh session (`backlog-slices.md`); or parallel subagents for independent parts (`dispatching-parallel-agents.md`), each told the steps below and not to commit. Isolation when the working tree is dirty: `using-git-worktrees.md`.
- **Test first, recorded:**
  1. Write every test `<change>`'s `## Acceptance tests` names, then one call before any of their code: `$V red AC-001 AC-002 …`, naming every AC that has a test. It records them failing; if any test passes, can't be found or can't run, nothing is recorded: fix those tests and rerun the batch. `manual` rows have no red step. A bug's AC-001 is the proving test from Define.
  2. Write the code. These steps are the test-first loop, so don't load `sdlc:test-driven-development`; load `sdlc:systematic-debugging` only the moment something fails unexpectedly. Work in batches, as plain Claude does: independent edits to code, tests and docs as parallel tool calls in one turn, then the nearby tests once, not after every edit. Never wait on a command with a sleep loop; a concurrency or kill test uses the fewest processes that show the behaviour.
  3. Once, at the end: `$V`. It runs the project's verify plan (lint, typecheck, build, the full suite), each AC's test, and the drift check. Fix until it passes.
- **Beyond the acceptance list.** Work from the spec's must-never-break lines and failure modes too, not only the ACs. A crash window in a write (a file or lock created and then written, a write and then a rename) is must-fix when the spec says a killed process must not leave the system unusable: write so a kill at any moment leaves a valid state, and test the kill at more than one moment.
- **Drift never stops Build.** Anything that changes from the plan (a task split, another file, an AC that can't be met as written) is one line, `state.py deviation <f> "<file or task> What: … Why: … Effect: …"`, and the build goes on. `$V` fails on a changed file nothing names until it has its line.
- **Parts:** each part ends with `$V` passing, one commit naming the record (`… (<change>)`), its row done (`backlog-slices.md`), and the state file's `## Handoff` updated so the next session can start from the files.
- `verify.py` doesn't read `.sdlc/baseline.md`: when only the test step fails and every failure is listed there, log it with `state.py log` and pass the gate.
- **Gate:** every task done; `$V` passes (every AC red first, now passing; every drift recorded) and prints `head <h> tree <t>`. Then one shell call moves to Review and gets its diff facts: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/state.py" verified <f> <h> <t> && python3 "${CLAUDE_PLUGIN_ROOT}/scripts/state.py" advance <f> 5 --gate pass && python3 "${CLAUDE_PLUGIN_ROOT}/scripts/diff_stats.py" --format md --base <Base> --plan <state>`.
- **Back from Review with findings:** fix each here with a failing test first. Fix the rule, not the instance: list the other cases it covers, and check the fix opens no new failure. Then `$V`, and `verified` and `advance <f> 5` in one call.
