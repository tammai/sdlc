# Define (Stage 1)

Before any code, you and the user agree on what, why and how, and it is written down in two places: `<intents>/change.md`, the record for people (why, what must be true and the test for each criterion; Review adds what was checked), and the state file's plan sections, the agent's (how the build runs, the tasks and their files, the public surface). Same sections at every size; S fills each in a few lines. Stay at `Current: Stage 1 – Define` until the gate, then `state.py advance <f> 4 --gate pass`.

**Nothing stays in your head.** A later session, a reviewer or a teammate months from now works from these two files alone. Test: could a fresh agent build this from them without asking?

1. **Read first.** If `knowledge/index.md` exists, read it and open only the docs relevant here; a recorded decision is a constraint unless the user agrees to revisit it (then a new record supersedes it). If `<docs>/recurring-defects.md` exists, read it: an entry that applies becomes an acceptance criterion. Read the code the change touches.
2. **Is it clear?** You judge. If the request, ticket, code and knowledge already say what, why and how (a stack trace with an obvious cause, a tightly specified change), go on to step 4. If anything that would change what gets built is missing or ambiguous, at any size, go to step 3 first.
3. **Ask, one question at a time.** Each question builds on the last answer or on something you found, says what the answer changes, and is one sentence. Propose a concrete answer when the user says "you decide". On L, use `sdlc:brainstorming` for the interview, telling it it runs under the orchestrator: it returns here with its design, which becomes `change.md`'s Why and Decisions. Stop asking when you can write the record without guessing anything that matters. Never ask the same thing again later.
4. **A bug: prove it first.** Before proposing a fix, show the bug exists: a failing test (preferred) or exact steps and what they show. Then find the root cause (`sdlc:systematic-debugging`: reproduce, isolate, test one idea at a time), not just the symptom. The proving test becomes the fix's first acceptance test (AC-001). The proof and the cause go in `change.md`.
5. **Keep to the brief.** Add no hardening, options, config or tooling that neither the request nor an applicable failure mode calls for. Anything else you'd add is listed as a proposal in `change.md` and dropped unless the user keeps it.
6. **Write the record**, once, in one turn: `change.md` from `${CLAUDE_PLUGIN_ROOT}/templates/change-template.md`, and the state file's plan sections, both with your file-writing tool, as parallel writes; then `state.py sync <f>`. UI work: read `ui-work.md` first.
   - **`change.md`**, everything above `## Review`: what the change is for and who it serves, why now, the user's own words where they matter, the decisions with what was ruled out and why (on L the design too; there is no `design.md`), for a bug its proof and root cause; acceptance criteria with ids (`AC-001` onward), each a behaviour a test can prove (about 10 or fewer, never "existing tests still pass"); `## Acceptance tests`, one row per AC with the test and a command that runs only it (`manual` with a reason when no test can prove it); the must-never-break lines; the failure modes that apply (concurrent use, scale, persisted data, a crash mid-write, untrusted input, I/O errors), each turned into a criterion or a must-never-break line; and what's out of scope.
   - **The state file's plan sections** (the agent's record; the one place you write the state file by hand after creating it): `## How the build runs` (step 7), `## Handoff` (what the builder needs and wouldn't find in the code: facts with file:line, risks), `## Tasks` (numbered, each naming its files in backticks: `verify.py` reports a changed file no task names as drift), `## Public Surface` (exports, endpoints, commands, config keys, env vars and dependencies the change adds or whose signature it changes, each with its AC; `- none` if none), and `## UI mapping` on UI work. `## Deviations` stays as `state.py deviation` writes it.
   - **Bigger than one session** (several distinct parts that won't fit one context; never a 1–2-file change): add `backlog.md` (`backlog-slices.md`), and `## Tasks` gives each part an outline (approach, main files, interfaces between parts).
7. **How the build runs** is your call, with its reason:
   - **inline** (default): this session builds it, like plain Claude;
   - **parts in fresh sessions:** the work won't fit one context; each part runs after `/clear` + `/sdlc:start`, or under autopilot (`backlog-slices.md`);
   - **parallel subagents:** only for truly independent parts (different files, no shared interfaces) where running them at once saves real time (`dispatching-parallel-agents.md`).
8. **Gate.**
   - **S:** no stop (`s-track.md`).
   - **M and L:** one short message; the files hold the detail, so don't restate them: the path to `change.md` (and `backlog.md`); a small table of the decisions (decision · chosen · ruled out), with how the build runs and any proposals you'd drop unless kept as rows; the acceptance criteria, one line each (`manual` ones marked, with reasons); and "Reply 'approved', or change anything." The user reads `change.md` and approves. Update the files for anything the reply changed (once), then `state.py advance <f> 4 --gate pass`.
   - Either way: every AC has a row in `change.md`'s `## Acceptance tests`; out of scope is filled; the two files stand alone.
