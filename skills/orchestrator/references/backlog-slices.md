# Backlog slices

For a feature too big for one session, so the work can pause, `/clear` and resume between slices, or run in fresh sessions (autopilot). S never gets a backlog; a feature that fits one session keeps its flow. Every slice runs Lite's inner loop, so read `lite-flow.md` too (its steps 2–4); its strike-out and size-up rules don't apply here.

1. **Backlog.** Copy `${CLAUDE_PLUGIN_ROOT}/templates/backlog-template.md` to `<intents>/backlog.md`: one row per vertical slice (something a test or user can see working end to end), with its FRs, acceptance criteria, dependencies and size. Every spec FR is in some row. **Approval:** on M (any risk: size the work while writing the spec), with the spec, in one message; on L, at the Stage 3 gate, replacing the plan and the execution-method question. `state.py set <f> Flow lite` in the same turn as that gate message, so the user's approval also accepts the trust anchor's `Flow:` notice.
2. **Flow.** `Flow: lite` at any track and risk. Lite's strike-out list doesn't apply: Stage 3 is each slice's plan, and L keeps Stage 2 and 11. Tiers per the core's table. The Lite size-up rule doesn't apply. `Base:` stays the feature's start; Stages 7, 8 and 11 run once, at Feature close.
3. **Pick the slice:** `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/backlog.py" next <intents>/backlog.md` (a slice in progress, else the first `todo` whose dependencies are done; `check <backlog> B<n>` for a named one, refused while its dependencies aren't done). Nothing ready while rows remain (a `blocked:` row, or open dependencies) → say which and stop; every row `done` → Feature close. Then `state.py slice <f> start B<n>` (sets `Slice:` and `Slice base:` and the row to `in progress`).
4. **Each slice** (Stage 3 → 4 → 5 → 6, with the usual stage headers and `state.py advance` at each move):
   - Plan (Stage 3): `<intents>/plan-B<n>.md`, short: 3–6 tasks, each naming its files, FR and test, plus a `## Public Surface` list. No planning skill.
   - Build (Stage 4) as in Lite step 2 (`Build:` decides). Verify (Stage 5): one fresh verifier (standard tier; top on risk high) whose brief names this slice's acceptance criteria (its backlog row); the full suite still covers the earlier slices; FAIL as in Lite step 3. Review (Stage 6) as in Lite step 4, on this slice only: diff facts with `--base <Slice base> --plan <intents>/plan-B<n>.md`, and `git diff <Slice base>`.
   - Commit: the core's verified-tree check (only that check; the rest of Stage 8 waits for Feature close), then one commit for the slice (code, tests, docs, plan, state) and `state.py slice <f> done B<n> <commit>` (in the next slice's commit, or a final docs commit). The commit-time security hooks run on it.
   - Then straight on to the next slice at Stage 3 (in an autopilot session, end instead).
5. **Gates.** `Slice gates: none` (default): slices run back to back without asking. They stop only for a failed gate (a second verifier FAIL), a backlog change that adds scope, or a hard stop (merge, deploy, migrations, anything irreversible). The user can opt in to stops at `plan`, `review` (show the findings before fixing) or `commit`: `state.py set <f> "Slice gates" "plan, commit"`.
6. **Backlog changes.** A slice that turns out too big, or work no slice covers: propose the change. A split that keeps the same FRs is made and logged (`state.py log`). Anything that adds scope (a new FR, or work outside the spec) waits for the user (`state.py blocker raise`); never add it silently.
7. **Context.** At a slice boundary, if the next slice won't fit in what's left of this session, stop with one line: `B<n> done (<commit>). Next: B<m> <title>. Run /clear, then /sdlc:start.` For a long backlog the user can run autopilot instead: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/autopilot.py" <feature>` from a terminal starts a fresh headless Claude Code session per slice, then one for Feature close, and stops on a blocked slice, a run that changed nothing, or an open trust-anchor notice. Off unless the user asks for it.
   **In an autopilot session** (the request ends with `--autopilot`): no one is there to answer. Run the one slice named (or Feature close), then end. Several active features: change nothing and end, saying why. A Feature close that can't reach Stage 8 (a second verifier FAIL, a high finding it can't fix): log why, raise it as a blocker, leave `Current:` where it stopped, and end. Never ask: `Slice gates` count as `none`, and anything that would ask (a failed gate, a scope-adding backlog change, a hard stop) runs `state.py slice <f> block B<n> "<reason>"` (the row and an open question) and ends the session. Feature close ends at Stage 8's merge, PR or keep question; ask it and end.
8. **▶ Feature close**, once every row is `done` (in a fresh session if this one is low on context; `/sdlc:start` lands here). Print the stage header for each step:
   - Verify (Stage 5): one fresh verifier round on the whole branch, over every acceptance criterion in the spec; a FAIL as in Lite step 3.
   - Review (Stage 6): the feature's one top-tier `sdlc:code-reviewer`, on `Base..HEAD`, with the diff facts (`--base <Base>` and one `--plan` per `plan-B*.md` in `<intents>`: the union of their Public Surface is what's declared) and a brief on how the slices fit together. Fixes as in Lite step 4.
   - Security (Stage 7): light, or full on L and `Risk: high` (`stage-7-security.md`).
   - Stage 8: the verified-tree check, then ask about merge, PR or keep (a hard stop). Stage 11 on L (`stage-9-11.md`). Then `state.py set <f> Status done`.
