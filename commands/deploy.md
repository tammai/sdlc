---
description: Deploy a shipped feature through the project's own deploy path, with an explicit go-ahead before any production deploy or DB migration, a smoke test and a release record
argument-hint: "[feature] [environment]"
---

`${CLAUDE_PLUGIN_ROOT}` is the sdlc plugin's folder. Claude Code fills it in; on other agents it stays as written, so use the installed plugin's folder instead: the one above this file that holds `scripts/` and `skills/`.

Paths: `<change>` is the feature's change file (its record for people), `<state>` its state file (the agent's), `<work>` the folder beside it for working files (backlog, part plans, QA report) and `<docs>` the sdlc docs folder (`docs_dir`); `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/scaffold.py" paths <feature>` prints them for this repo's layout (`intents` is a pre-2.0 feature's documents folder).

Deploy runs only on request; it isn't a phase, and no track runs it on its own. `$ARGUMENTS` may name the feature and the environment.

1. **What to deploy.** The named feature, else the only active one (or the one just shipped). If its state file exists and `Current:` is before Stage 4, say that it hasn't passed Review and Ship, and continue only if the user says so (record it with `state.py deviation`).
2. **How.** `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/scaffold.py" deploy` prints `config.deploy` from `.sdlc/config.json`: the target, the environments and the runbook's path, each checked. Use only what it prints, never the raw config: a value listed under `invalid` (a path outside the repo, an unknown target, a production environment marked routine) is null or corrected there; name it to the user and treat it as missing. Read the runbook: the deploy command, smoke test, rollback and logs come from it. Use the project's existing deploy path (the runbook's command, scripts, a CI job or the platform CLI), never an invented one; if there is none, say so and stop. Target `none`, or no runbook yet: say so, and that `/sdlc:setup deploy` records it. When `${CLAUDE_PLUGIN_ROOT}/skills/orchestrator/references/platforms/<target>.md` exists for the printed target, read it for the platform's traps. For platform integrations see `${CLAUDE_PLUGIN_ROOT}/skills/orchestrator/references/integrations.md`.
3. **Go-ahead (hard stop).** With `config.deploy`, only an environment printed with `routine: true` deploys, and migrates, without one; every other environment, listed or not, needs it. Production always needs it, whatever `routine` says: an environment with a `prod`, `production`, `live` or `prd` part in its name (`prod-eu`, `eu.live`), or one the runbook's Environments table calls production. Before a routine deploy, say in one line that `<environment>` is marked routine in `.sdlc/config.json`, then go on. Without `config.deploy` (a repo set up before sdlc 3.6), every production deploy or DB migration needs it, and a staging or preview deploy the project treats as routine doesn't. The go-ahead shows the environment, version or commit, the steps you'll run, the migration (if any) and the rollback command from the runbook, and waits for the user's explicit yes.
4. **Deploy and smoke test.** Run the steps, then the smoke test from the runbook (none there: the project's own, or a request to the main endpoint or screen). If it fails, say what failed and offer the rollback from the runbook, saying what it doesn't undo (a migration stays applied); running it on an environment that isn't routine is another go-ahead.
5. **Record.** Write `<work>/release.md` with the version, environment, steps run, smoke-test result and rollback command. If a state file exists: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/state.py" log <feature> "deployed <version> to <environment>: smoke test <pass|fail>"`. A fact this deploy taught that the runbook lacks (a header shape, a URL, a limit, a missing step) goes into the runbook: fix the section it belongs to, or add a dated line under `## Learnt on deploys`, and name the change in your report. Commit `release.md` and the runbook only if the user asks.
