# Spec 05: Security

Security feedback runs continuously while code is written. A model security review of the feature, in Review and on the commit, runs only when the change is **security-touched**: `Risk: high`, or the diff since `Base:` touches `areas.sensitive` or `areas.migrations`. In Review it is recommended then, and chosen by the user on M and L ([ADR 0020](../adr/0020-sdlc-2-slim-process-core.md)). The turn-end review runs only then too, and outside an active feature neither runs ([ADR 0019](../adr/0019-model-security-review-only-for-security-touched-work.md)).

**Entry points:** always-on hooks; Review (Stage 5) of the orchestrator · **Source:** `hooks/security_reminder_hook.py` and modules, `hooks/sdlc_review_gate.py`, `templates/project/config.defaults.json` (the default `areas`), `hooks/sg-python.sh`, `hooks/ensure_agent_sdk.py`, `hooks/patterns.py`, `skills/orchestrator/references/review.md`, `review-brief.md`, `templates/project/rules/sensitive.md`, `templates/project/hookify/sdlc-secret-values.md`

## User scenarios

1. **Risky edit.** When Claude writes code matching a known-dangerous pattern (e.g. `eval`, `innerHTML`, `pickle.loads`), then a short warning is added to Claude's context.
2. **End of turn.** Given an active feature whose change is security-touched, when Claude finishes a turn that changed code, then the changed lines are reviewed by a model and findings come back for Claude to address.
3. **Payments feature.** Given work touching payments, then it's at least M with `Risk: high`, and Review recommends the security review: a `code-reviewer` with the security brief and a dependency audit.
4. **Plain change.** Given an active feature at `Risk: low` whose diff touches no sensitive or migration path, when its review-ready commit is made (the state file included), then no model reviews it (it is recorded as reviewed), and Review doesn't recommend a security review unless untrusted input reaches a shell, file path or database; the pattern warnings still ran while it was written, and no turn-end review did.

## Non-goals

- Deep vulnerability scanning, SAST/DAST suites, dependency monitoring (Anthropic's `claude-security` isn't bundled; see `skills/orchestrator/references/integrations.md`).

## Known gaps

- SEC-FR-009's limits come from the repo, which the reviewed agent can write: it could move a branch ref, or edit the reviewed-commits record in `.git`, to defer more. As with the trust anchor (spec 02), this makes skipping visible work rather than impossible; the push review and Review's security review, when chosen, still run.
- Whether a change is security-touched comes from `Risk:` in the state file, which the agent being reviewed can write (the trust anchor reports a lowered `Risk:`), and from the areas. The plugin's default areas always apply and the config can only add to them, so they can't be narrowed, but a project-specific sensitive path the defaults miss gets no model review unless it is added to `.sdlc/config.json`.
- On M and L the security review is the user's choice: a security-touched change whose review the user declines rests on the hooks and the commit review.
- A change that isn't security-touched, and any work outside an sdlc feature, rests on the pattern hooks and the push review; no model reviews it at turn end or on commit (ADR 0019).
- A widened commit review (SEC-FR-009) still goes through the reviewer's 30-file prioritiser; files it drops are recorded as reviewed with the rest, as for any large commit.

- The security-guidance hooks are vendored and not covered by this repo's tests; behavior is upstream's. The reviewer environment has not yet been built on this machine (doctor reports it).
