# Spec 04: Verification

Build produces the evidence and Review reuses it ([ADR 0013](../adr/0013-build-proves-prove-judges.md), [ADR 0020](../adr/0020-sdlc-2-slim-process-core.md)): every acceptance criterion has a named test, listed in the change file beside it, that failed before its code and passes now, checked by one command (`verify.py`) at every size. Review doesn't rerun it unless the code changed, and a hook won't let Review finish on stale test results. A QA run of the feature that doesn't look at the code is available on request.

**Entry points:** Build (Stage 4) and Review (Stage 5) of the orchestrator · **Source:** `scripts/verify.py`, `skills/orchestrator/references/build.md`, `skills/orchestrator/references/review.md`, `agents/qa-tester.md`, `hooks/verify_freshness.py`, `hooks/prove_budget.py` (Review's command budget; the file name is kept from 1.x), `hooks/trust_anchor.py` (the Stage 5 passage, verify records), `templates/change-template.md` (`## Acceptance tests`), the state template in `references/start.md` (tasks, Public Surface, Deviations), `templates/project/baseline.md`

## User scenarios

1. **Reuse.** Given Build recorded each AC's test red and then ran a passing `verify.py`, when Review finds the code unchanged (`verify.py status` says `reuse: true`), then nothing is rerun and the run is Review's evidence.
2. **Stale results.** Given Review and a full test run, when code changes afterwards (by any tool, including a formatter or subagent), then finishing the turn is blocked with the reason and the exact command to rerun.
3. **Monorepo.** Given packages `api` and `web`, both fresh, when `services/api/handler.go` changes, then only `api` is stale and the block names `cd services/api && go test ./...`.
4. **Test that proves nothing.** Given a test that passes before its code exists, then `verify.py red` refuses it and records nothing, so `verify.py` fails until the test fails first.
5. **Drift.** Given Build changed a file no task or acceptance test names, then `verify.py` fails until the state file's `## Deviations` has a line naming the file with What:, Why: and Effect: (`state.py deviation`); Build goes on, and the end of Review lists the drift.
6. **QA on request.** Given the user asks for a QA round, when the `qa-tester` runs an acceptance scenario and doesn't see the spec's *Then*, then it reports the steps and observed output, and the user decides what the failure means.

## Edge cases

- Stop with no git repo: edit-tool tracking only (no worktree diff).
- A worktree diff that can't be computed (tree garbage-collected, slow repo over 5 s) leaves the state as it was rather than blocking.

## Non-goals

- Judging whether tests are good (that's the code review's test-gap pass, when a code review runs); running tests itself.
- The qa-tester writing tests into the repo; e2e or visual-regression suites; load testing beyond a stated criterion; mutation testing.

## Known gaps

- A red record shows the test failed when `verify.py red` ran; it doesn't prove the AC's code was absent then (that would cost a checkout per stack). When no code review runs (an S change recommended none, or the user declined it), nothing reads the tests against their criteria, so a test that runs and passes but asserts the wrong thing is caught only by its red record.
- The role-guard hook stops the qa-tester's Read, Grep and Glob on project files outside `.sdlc/`, the docs folder and READMEs. It keeps Bash, so `cat src/…` is still only instructed against.
- The 2-minute limit is enforced in Claude Code only (VER-FR-041); other hosts' command payloads haven't been checked for a field to change, so there it is an instruction. A compound non-project command is refused, so agents split it into calls. Without a `timeout` binary (macOS without coreutils) the hook only lowers the tool timeout, which backgrounds a long command rather than killing it. A probe chained after a project command (`npm test; node probe.js`) counts as the project's own and escapes the limit. The qa-tester's 10-minute total and probe cap are instructions.
- `verify.json` and the hook's copy are both in `.sdlc/.work/`, which the agent can write (`verify.py` writes both on every full or `red` run, so a disagreement comes only from a later edit): an edit to one shows as "verify records disagree" (VER-FR-053), and Review won't reuse the run, but nothing prevents editing both. Tampering is evident, not prevented.
- The hook copies `verify.json`'s entry when its tree matches the current code, so an entry edited by hand in the same call as the run would be copied too; an edit in a later call no longer matches the copy and shows as "verify records disagree".
- `verify.py` fails on any non-zero exit from the verify plan; it doesn't read `.sdlc/baseline.md`, so a baselined failure in the suite fails it too. Build then checks the output against the baseline by hand: when only the test step fails and every failure is listed there, it logs that and passes the gate (`build.md`).
- The drift check covers files, tasks and the Public Surface; an AC's test renamed or moved shows only as a missing file or a failing row.
- `verify.py`'s 1.x fallback (reading `spec.md` and `plan.md` when the state file has no `## Tasks`) and the `head <h> tree <t>` line a passing run prints have no test of their own.
- `.only` inside a test file and unusual custom filters aren't detected by the hook (a guardrail warns on `.only` instead).
- Hooks fire for tool calls inside subagents (checked in a headless session on 2026-10-23; the input names the agent in `agent_type`), and the worktree diff at the turn's end covers their edits regardless.
- Two features in Review at once: the state is named after the first one found, but freshness is about the worktree's code, which they share, so both are guarded.
- A run that exceeds the hook's 10-second timeout is killed by Claude Code and leaves no error marker.
