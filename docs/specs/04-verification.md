# Spec 04: Verification

Build produces the evidence and Prove (Stage 5) judges it ([ADR 0013](../adr/0013-build-proves-prove-judges.md)), on M full and L only ([ADR 0015](../adr/0015-prove-only-where-it-pays.md): S and M lite go from Build's passing `verify.py` to Ship, every backlog gets one Prove at Feature close, and the user may skip Prove on M full and L): every acceptance criterion has a named test that failed before its code and passes now, checked by one command (`verify.py`), and a fresh agent reads each test against its criterion. Prove decides whether the work does what the spec says, using evidence that is fresh, independent and honest about pre-existing failures. A QA run of the feature that doesn't look at the code is available on request.

**Entry points:** Prove (Stage 5) of the orchestrator · **Source:** `scripts/verify.py`, `skills/orchestrator/references/build.md`, `skills/orchestrator/references/prove.md`, `agents/ac-checker.md`, `agents/verifier.md`, `agents/qa-tester.md`, `hooks/verify_freshness.py`, `hooks/prove_budget.py`, `hooks/trust_anchor.py` (the Stage 5 passage, verify records), `templates/plan-template.md` (`## Acceptance tests`, Deviations), `templates/project/baseline.md`

## User scenarios

1. **Pass on the first round.** Given Build recorded each AC's test red and then ran a passing `verify.py`, when Prove finds the code unchanged (`verify.py status` says `reuse: true`) and a new checker says every test proves its criterion, then the round is PASS and the gate passes, with nothing rerun.
2. **Stale results.** Given Prove and a full test run, when code changes afterwards (by any tool, including a formatter or subagent), then finishing the turn is blocked with the reason and the exact command to rerun.
3. **Monorepo.** Given packages `api` and `web`, both fresh, when `services/api/handler.go` changes, then only `api` is stale and the block names `cd services/api && go test ./...`.
4. **Old failure.** (Old plans; `verify.py` doesn't read the baseline, see Known gaps.) Given a failure listed in `.sdlc/baseline.md`, when the verifier sees it, then it doesn't fail the round; if a listed failure now passes, the verifier removes it.
5. **Scenario broken in use.** Given a backlog feature whose tests all pass, when the `qa-tester` in its Feature close round runs User Story 1 scenario 2 and doesn't see the spec's *Then*, then it reports the steps and observed output, and the failure goes back to Build with the round's other findings, fixed failing test first, before the re-verification.
6. **Test that proves nothing.** Given a test that passes before its code exists, then `verify.py red` refuses it and records nothing, so `verify.py` fails until the test fails first. Given a test that runs and passes but only asserts a status code, then on M full and L the checker (M: the code-reviewer; L: the ac-checker) says it doesn't prove its criterion and the round fails; on S and M lite nothing reads it (Known gaps).
7. **Round cap and repeated failure.** Given three failed rounds, or the same requirement failing in two rounds, then the orchestrator stops and brings the user what still fails, what each round changed, and a root-cause hypothesis.
8. **Drift.** Given Build changed a file no task or acceptance test names, then `verify.py` fails until `## Deviations` has a line naming the file with What:, Why: and Effect:; Build goes on, and the end of Prove lists the drift.

## Edge cases

- Stop with no git repo: edit-tool tracking only (no worktree diff).
- A worktree diff that can't be computed (tree garbage-collected, slow repo over 5 s) leaves the state as it was rather than blocking.

## Non-goals

- Judging whether tests are good (that's the ac-checker, the verifier on old plans, and the code reviewer's test-gap pass); running tests itself.
- The qa-tester writing tests into the repo; e2e or visual-regression suites; load testing beyond a stated SC; mutation testing.
- QA on the S track.

## Known gaps

- The role-guard hook stops the qa-tester's Read, Grep and Glob on project files outside `.sdlc/` and READMEs, and the verifier's file edits outside its report, the baseline, its red-green worktree and its probe scripts. Both keep Bash, so `cat src/…` or a `sed` edit is still only instructed against. The qa-tester runs by default only at Feature close (and on request elsewhere): on M full it was the critical path of Prove (24 minutes in eval r12) and is dropped (ADR 0012), so M full gives up black-box probing.
- The 2-minute limit is enforced in Claude Code only (VER-FR-041); other hosts' command payloads haven't been checked for a field to change, so there it is an instruction. A compound non-project command is refused, so agents split it into calls. Without a `timeout` binary (macOS without coreutils) the hook only lowers the tool timeout, which backgrounds a long command rather than killing it. A probe chained after a project command (`npm test; node probe.js`) counts as the project's own and escapes the limit. The 10-minute total, the probe cap and the two-round stop are instructions: nothing measures the total or counts probes.
- A red record shows the test failed when `verify.py red` ran; it doesn't prove the AC's code was absent then (that would cost a checkout per stack). The checker reading the test is the check on a test that fails for the wrong reason.
- `verify.json` and the hook's copy are both in `.sdlc/.work/`, which the agent can write (`verify.py` writes both on every full or `red` run, so a disagreement comes only from a later edit): an edit to one shows as "verify records disagree" (VER-FR-053), and Prove won't reuse the run, but nothing prevents editing both. Tampering is evident, not prevented.
- The hook copies `verify.json`'s entry when its tree matches the current code, so an entry edited by hand in the same call as the run would be copied too; an edit in a later call no longer matches the copy and shows as "verify records disagree".
- S and M lite have no Prove ([ADR 0015](../adr/0015-prove-only-where-it-pays.md)), and neither does M full or L with `Prove: skip`: no checker reads their tests, so a test that runs and passes but asserts the wrong thing is caught only by its red record (it must fail before its code). They never enter Stage 5, so the freshness hook's block and the prove-budget limit don't apply; Ship's verified-tree check catches code changed after the passing run.
- On S the only acceptance test is the state file's `Repro:` line. The trust anchor watches it like spec.md only from Stage 5 on; S never enters Stage 5, so `Repro:` is anchored only at Ship, and may change freely during Build. The same holds for spec.md on M lite and `Prove: skip`. With no plan, drift isn't checked on S.
- `verify.py` fails on any non-zero exit from the verify plan; it doesn't read `.sdlc/baseline.md`, so a baselined failure in the suite fails it too. Prove's session then checks the output against the baseline by hand (`prove.md`), and the trust anchor's Stage 5 check, which needs a passing run, reports it to the user. Build's gate has no such escape, so on S, M lite and `Prove: skip` (no Prove) a baselined failure keeps Build from passing.
- The drift check covers files, tasks and the Public Surface; an AC's test renamed or moved shows only as a missing file or a failing row.
- Old plans: red-green runs `install` in a fresh worktree each round: it takes time and may use the network.
- Old plans: red-green on a refactor: tests that pass on Base are expected, and the verifier lists them; a criterion relying only on such a test has no evidence.
- `.only` inside a test file and unusual custom filters aren't detected by the hook (a guardrail warns on `.only` instead).
- Hooks fire for tool calls inside subagents (checked in a headless session on 2026-10-23; the input names the agent in `agent_type`), and the worktree diff at the turn's end covers their edits regardless.
- Two features in Prove at once: the state is named after the first one found, but freshness is about the worktree's code, which they share, so both are guarded.
- A run that exceeds the hook's 10-second timeout is killed by Claude Code and leaves no error marker.
