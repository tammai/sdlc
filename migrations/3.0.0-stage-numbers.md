summary: sdlc 3.0 numbers the phases 1 to 4 (Define, Build, Review, Ship); state files move from Process 2 to Process 3
---

sdlc 2.x numbered the four phases 1, 4, 5 and 8, left over from the eleven-stage pipeline. 3.0 numbers them 1, 2, 3 and 4 (`Current: Stage 2 – Build`) and marks a state file `Process: 3`. The hooks and `state.py` act only on `Process: 3`, so a 2.x feature left as it is gets no guard and `state.py` refuses it until it is migrated. Nothing else about the flow changes.

1. **Renumber the state files.** Run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/state.py" migrate` in the repo. It rewrites every `Process: 2` state file, finished features too: the `Current:` line, the Stages checklist and the Gate log, and it drops the trust anchor's remembered stage for each (a git-ignored file). It prints `migrated` and `skipped`; a skipped feature holds a stage number it can't map: show the user its reason and leave it. It is safe to run twice. It only sees the state files on the branch that is checked out: a feature on a branch that isn't merged yet still has `Process: 2`. Tell the user to run the same command on each such branch once it has this upgrade merged in (`git branch --no-merged` lists them); until then `state.py` refuses that feature and says so.
2. **Regenerate** every entry in `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/scaffold.py" upgrade-plan` → `regenerate`: `.github/workflows/sdlc-invariants.yml`'s check (`.sdlc/ci/invariants.py`) now counts Build as stage 2 and Ship as stage 4 on a `Process: 3` feature (a 2.x one keeps the old numbers until step 1 runs).
3. **Companion plugins.** If the repo uses `sdlc-stepper`, tell the user to update it to 3.0.0 as well; the old one only reads `Process: 2` and shows no bar for a migrated feature.
4. **Commit** `chore(sdlc): upgrade to 3.0` with the migrated state files. Point the user at the 3.0.0 section of the plugin's CHANGELOG.
