From 2.3.0 setup asks where the keys that turn sdlc on go. `.claude/settings.local.json` is never committed, so a teammate's clone runs without sdlc and its companions. `$S enable-plugin --team` writes them to the committed `.claude/settings.json` instead (a cloud session installs no plugin from that file: tell a user who works there about the guidebook's "Cloud sessions" routes); turning a conflicting plugin off (superpowers) stays in the local file.

1. Look at `$S upgrade-plan` → the lock's `merged` entry `.claude/settings.json#plugin`. Not empty: the team file already holds them; apply this migration.
2. Otherwise ask, as setup's `enable-plugin` step does: **keep them on this machine only** (skip this migration with that reason) or **commit them for the team** (recommended when the user wants teammates on sdlc). Committing also offers sdlc to every teammate who trusts the repo.
3. Commit → `$S enable-plugin --team`, plus `--with <id>` for each companion already on in `.claude/settings.local.json` (see `companions` in its result), then commit `.claude/settings.json` as `chore(sdlc): sdlc enabled for the team`. The local keys can stay; they agree.
