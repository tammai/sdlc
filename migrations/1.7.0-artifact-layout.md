summary: Move sdlc documents to docs/sdlc (or a location you choose); feature state stays in .sdlc/state

1.7.0 splits what people read from what the plugin runs on. Documents (constitution, design system, each feature's brainstorm, spec, design, plan and reports) move to `docs_dir` (default `docs/sdlc`, features in `<docs_dir>/intents/<name>/`). State moves to `.sdlc/state/<name>.md`. Config, lock, baseline, `ci/`, `lint/` and `.work/` stay. Until this runs, the hooks read the old layout and doctor warns.

1. **Location.** `$S status` → `docs_site`. If it names a file, the repo builds a site from `docs/`, so `docs/sdlc` would be published: say so and ask where the documents go (`.sdlc` itself, a path of their choice inside the repo, or `docs/sdlc` anyway). Otherwise use `docs/sdlc` without asking.
2. **Preview.** `$S relocate --docs-dir <d>` (dry run) lists every move. List the features whose state says `Status: active` and warn that their open branches will see the files renamed (git follows renames on merge, but in-flight branches should merge or rebase after this lands). The user confirms.
3. **Move.** `$S relocate --docs-dir <d> --apply`. It needs a clean tree, and it is all or nothing: if it reports `conflicts` (a feature in both layouts, or a target document that already exists), nothing has moved. Show the user both copies, let them pick, commit, and run it again. `docs_dir` is recorded with the move. Files git ignores (`.DS_Store`) stay behind in the old folder; delete them.
4. **Re-render.** The upgrade regenerated the policy rules before this migration ran, so they still name the old paths: run `$S render` again for every entry in `$S upgrade-plan` → `regenerate`, and for the seeded `.claude/hookify/sdlc-ui-hardcoded-values.md` with `--class seeded --if-unchanged`.
5. **Commit** `chore(sdlc): move sdlc documents to <d>`.
