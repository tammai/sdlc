summary: Choose who does UI design work, sdlc's builtin design system or the impeccable skill (repos with UI only)
---

From 2.1 a repo with UI records a design mode: `builtin` (the design system, rule and guardrail sdlc has always had) or `impeccable` (the impeccable skill does the design work; sdlc keeps the gates and the review verdict). A repo without the key stays `builtin`, so nothing changes unless the user picks impeccable.

1. No UI (no file matches `areas.ui`): skip this migration with that reason.
2. `$S design` prints the mode. Ask the user, with setup's recommendation from the PRD (the setup skill's `references/design-mode.md`). Builtin, or no answer: `$S design builtin` and this migration is done.
3. impeccable: follow the same step, `references/design-mode.md` in the setup skill (install and enabled check, `init`, `document`, the hook, the pointer in `<docs>/design-system.md`). `$S design impeccable` removes `.claude/hookify/sdlc-ui-hardcoded-values.md` once impeccable's detector hook runs here (it does the same job); a `guardrail.ask` in its result means the team edited it: ask the user before deleting it. A plugin turned on with `--enable` loads next session: skip this migration with that reason and tell the user `/sdlc:setup design` finishes it after a restart.
4. Commit `chore(sdlc): design mode – <mode>`.
