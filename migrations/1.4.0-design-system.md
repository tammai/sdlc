1.4.0 checks UI work against a design system. The UI policy rule (`.claude/rules/sdlc-ui.md`) and the hard-coded-values guardrail (`.claude/hookify/sdlc-ui-hardcoded-values.md`) arrive in the upgrade's *add* step; this migration covers the part the project owns.

1. Check `areas.ui` (`$S config`) against the repo's real UI paths and propose overrides in `.sdlc/config.json` if they differ (e.g. `lib/**/*.dart` for Flutter).
2. If no file matches `areas.ui`, the repo has no UI: mark this migration skipped with the reason "no UI".
3. If `.sdlc/design-system.md` is missing, run the `design-system` step from `skills/setting-up-projects/SKILL.md`: find the existing system and write the file from `templates/design-system-template.md`, pointing at it, or propose a library and minimal token set if there is none. The user approves the file.
